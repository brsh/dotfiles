# WSL2 Interoperability

<!-- Trigger note: this file is set to always_on, which injects it into every

These rules apply when working in or targeting WSL2 environments, particularly
the common pattern of running Linux tools from Windows or calling Windows
executables from inside a WSL2 distro.

---

## Environment Context

- WSL2 uses a real Linux kernel in a Hyper-V lightweight VM
- Files on the Windows filesystem are mounted under `/mnt/c/`, `/mnt/d/`, etc.
- Files native to WSL live on an ext4 virtual disk (`%LOCALAPPDATA%\Packages\...\ext4.vhdx`)
- Windows and WSL2 share networking but have separate localhost (with some bridging)
- Windsurf/VS Code use the WSL Remote extension to edit files natively in the WSL filesystem

## Path Translation

### wslpath — the right way to convert paths

```bash
# Windows path → WSL path
wslpath 'C:\Users\brian.sheaffer\Scripts'
# Returns: /mnt/c/Users/brian.sheaffer/Scripts

# WSL path → Windows path
wslpath -w '/home/brian/scripts/myscript.sh'
# Returns: \\wsl.localhost\Ubuntu\home\brian\scripts\myscript.sh

# Windows path → WSL path (with -u flag, explicit)
wslpath -u 'C:\temp\output.txt'
# Returns: /mnt/c/temp/output.txt

# In scripts — use wslpath to build portable paths
WIN_SCRIPTS=$(wslpath 'C:\Scripts')
OUTPUT_FILE=$(wslpath -u "$USERPROFILE\\output.txt")
```

### In PowerShell (calling from Windows into WSL)

```powershell
# Convert Windows path for use in WSL command
$wslPath = wsl wslpath -u "C:\Scripts\myscript.sh"

# Or run WSL with a Windows path directly (WSL auto-converts /mnt/c/ style)
wsl bash /mnt/c/Scripts/myscript.sh
```

### Accessing WSL files from Windows Explorer / PowerShell

```powershell
# WSL files are accessible via UNC path on Windows
\\wsl.localhost\Ubuntu\home\brian\
\\wsl$\Ubuntu\home\brian\          # older syntax, still works

# From PowerShell
Get-ChildItem "\\wsl.localhost\Ubuntu\home\brian\scripts"
Copy-Item "\\wsl.localhost\Ubuntu\home\brian\output.log" "C:\Logs\"
```

## File Permissions and Ownership

### The DrvFs vs ext4 Difference

Files on `/mnt/c/` (Windows filesystem via DrvFs) behave differently from files
on the WSL native filesystem (`/home/`, `/opt/`, etc.):

| | WSL native (ext4) | Windows mount (/mnt/c/) |
|-|-------------------|------------------------|
| `chmod` works | Yes | Metadata only — not enforced by Windows |
| `chown` works | Yes | No — always owned by WSL user |
| Execute bit | Respected | Configurable via `/etc/wsl.conf` |
| Symlinks | Full support | Limited support |
| Performance | Fast | Slower (filesystem translation overhead) |

```bash
# /etc/wsl.conf — configure DrvFs mount behavior
[automount]
options = "metadata,umask=022,fmask=111"
# metadata: enables chmod/chown to persist on Windows files
# umask=022: new files get 644 permissions
# fmask=111: files are not executable by default
```

```bash
# Scripts should live on the WSL native filesystem for:
# - Correct permission handling
# - Best performance
# - Predictable behavior with chmod/chown

# Bad: editing and running scripts from /mnt/c/
/mnt/c/Scripts/myscript.sh    # permission bits unreliable

# Good: work in WSL home directory, copy results to Windows if needed
~/scripts/myscript.sh
cp ~/output.csv $(wslpath -u "C:\Reports")
```

### SSH Keys in WSL

SSH key files must have correct permissions — Windows-mounted files often don't:

```bash
# If your key lives on /mnt/c/ — copy it to WSL native storage
cp /mnt/c/Users/brian.sheaffer/.ssh/id_ed25519 ~/.ssh/
chmod 600 ~/.ssh/id_ed25519
chmod 700 ~/.ssh

# Never leave SSH keys at /mnt/c/... and use them directly
# SSH client will refuse keys with too-open permissions
```

## Calling Windows Executables from WSL

Any `.exe` in the Windows PATH can be called from WSL directly:

```bash
# Call PowerShell (Windows PowerShell 5.1)
powershell.exe -Command "Get-Service | Where-Object Status -eq Running"

# Call PowerShell 7 (if installed on Windows)
pwsh.exe -Command "Get-ADUser -Identity brian.sheaffer"

# Pass a script file (use wslpath to get Windows-format path)
powershell.exe -File "$(wslpath -w ~/scripts/Invoke-Cleanup.ps1)"

# Call other Windows tools
notepad.exe /mnt/c/Users/brian.sheaffer/file.txt
explorer.exe .         # open current WSL directory in Windows Explorer
cmd.exe /c "dir C:\\"

# Windows environment variables are NOT automatically available in WSL
# Access them via cmd.exe or powershell.exe, or read from /mnt/c/...
```

### Passing Data Between WSL and PowerShell

```bash
# Pipe output from a PS cmdlet into a bash pipeline
powershell.exe -Command "Get-ADComputer -Filter * | Select-Object -ExpandProperty Name" \
    | sort | uniq > computers.txt

# Run a PS script and capture its CSV output in bash
powershell.exe -File "$(wslpath -w ~/scripts/Get-Report.ps1)" > /tmp/report.csv
csvkit ctail /tmp/report.csv | head -20

# Pass a bash variable into a PS command
SERVER="web01"
powershell.exe -Command "Test-NetConnection -ComputerName '$SERVER' -Port 443"
```

## Calling WSL from Windows PowerShell

```powershell
# Run a bash command from PowerShell
wsl ls -la /home/brian/scripts

# Run a bash script
wsl bash ~/scripts/check-services.sh

# Pipe PowerShell output into a WSL command
Get-Content .\servers.txt | wsl sort | wsl uniq

# Run in a specific distro
wsl -d Ubuntu-22.04 -- bash -c "apt list --installed 2>/dev/null | grep nginx"

# Run as a specific user
wsl -d Ubuntu -u root -- systemctl status nginx

# Execute a WSL command and capture output in PowerShell
$result = wsl df -h / | Select-String "/"
```

## WSL2 Distro Management

```powershell
# List installed distros
wsl --list --verbose    # shows name, state, and WSL version

# Set default distro
wsl --set-default Ubuntu-22.04

# Shut down all running distros (frees memory)
wsl --shutdown

# Export a distro as a backup
wsl --export Ubuntu-22.04 "C:\WSL-Backups\ubuntu-22.04-$(Get-Date -Format yyyyMMdd).tar"

# Import a distro (restore or create from exported tar)
wsl --import Ubuntu-Restored "C:\WSL\Ubuntu-Restored" "C:\WSL-Backups\ubuntu-22.04-backup.tar"

# Remove a distro
wsl --unregister Ubuntu-22.04    # WARNING: deletes all data in that distro
```

### Enabling systemd in WSL2

WSL2 supports systemd on modern builds (Windows 11 22H2+ / WSL 1.0.0+):

```bash
# /etc/wsl.conf — enable systemd
[boot]
systemd=true

# Then from PowerShell:
# wsl --shutdown   (required after editing wsl.conf)
# wsl              (restart the distro)

# Verify
systemctl --no-pager list-units --state=running
```

With systemd enabled, `systemctl`, `journalctl`, timers, and socket activation
all work as they would on a real Linux system.

## Networking Between WSL2 and Windows Host

```bash
# WSL2 has its own virtual network adapter
# The Windows host IP from inside WSL2 (WSL2 default gateway)
ip route show default | awk '{print $3}'   # usually 172.x.x.1

# Or use the hostname resolution (modern WSL2 with mirrored networking)
# Windows host is reachable at: $(hostname).local

# WSL2 with mirrored networking (Windows 11 22H2+, WSL 2.0+)
# /etc/wsl.conf:
[wsl2]
networkingMode=mirrored      # WSL shares Windows network stack (same IPs)
```

```powershell
# From Windows — find the WSL2 IP
wsl -- ip addr show eth0 | Select-String "inet " | ForEach-Object {
    ($_ -split '\s+')[3] -replace '/.*',''
}
```

## Windsurf / VS Code WSL Remote

When editing WSL files via the Remote-WSL extension:
- The terminal opens inside WSL — `bash`, `python3`, `dotnet` are the WSL versions
- PowerShell opened inside WSL runs PS 7+ (if installed in WSL), not Windows PS
- File paths in the editor are WSL paths (`/home/brian/...`) not Windows paths
- `code .` from inside WSL opens Windsurf with WSL Remote automatically
- Extensions are installed separately for WSL vs Windows — some may need reinstalling

## Common Pitfalls to Flag

- Scripts on `/mnt/c/` with `chmod +x` that "don't work" → permissions not enforced on DrvFs; move to WSL native filesystem
- SSH keys copied to `/mnt/c/Users/.../.ssh/` → wrong permissions; copy to `~/.ssh/` and set 600
- Line endings: files created on Windows have CRLF, scripts run in WSL need LF → use `.gitattributes` with `eol=lf` for shell scripts
- `localhost` from WSL2 does not reach Windows host services by default (use the gateway IP or enable mirrored networking)
- `wsl --shutdown` needed after editing `/etc/wsl.conf` — changes don't apply to running distros
- Running `apt update` / `pacman -Syu` inside WSL as root and forgetting the WSL user's sudo needs — WSL root and your user are different
- Storing large working files on `/mnt/c/` → significant performance penalty; keep active work on WSL native ext4
- `powershell.exe` from WSL is Windows PowerShell 5.1, not PS 7 — use `pwsh.exe` for PS 7
